# 08 — Глобальный массив лежит прямо в бинарнике

Локальный массив создаётся на стеке во время работы программы. А вот
**глобальный инициализированный** массив компилятор записывает прямо в файл
программы — его байты физически лежат в бинарнике ещё до запуска.

Куда именно попадает массив, зависит от того, как он объявлен:

| объявление | секция | что в файле |
|------------|--------|-------------|
| `int g[] = {1,2,3};` (глобальный, с ненулевыми значениями) | `.data` | **байты хранятся в файле** |
| `const int g[] = {...};` | `.rodata` | байты в файле (только чтение) |
| `int g[256];` (глобальный, без значений) | `.bss` | **только размер**, байтов нет |
| `int g[4] = {...};` внутри функции | стек | в файле нет вообще |

`.data`/`.rodata` — это тип секции **PROGBITS** («есть байты в файле»),
а `.bss` — **NOBITS** («байтов нет, при запуске обнулить»).

## Сборка

```bash
gcc -O0 -std=c11 -Wall -Wextra app.c -o app && ./app
```

Программа печатает адреса и первые значения `global_data`, `global_ro`,
`global_bss` и локального массива — дальше находим их в самом файле.

## 1. В какой секции лежит каждый массив: `nm`

Буква = секция символа: `D` = .data, `R` = .rodata, `B` = .bss.

```bash
nm app | grep -i global
```
```
0000000000004010 D global_data     <- .data
0000000000002008 R global_ro       <- .rodata
0000000000004040 B global_bss      <- .bss
```

## 2. Байты массива ПРЯМО в файле: `readelf -x`

Дамп секции `.data`. По адресу символа `global_data` (0x4010) видим ровно
наши значения `{0x11223344, 0x55667788, 0x77665544, 0x33221100}` — в
little-endian порядке байт:

```bash
readelf -x .data app
```
```
  0x00004010 44332211 88776655 44556677 00112233  D3"..wfUDUfw.."3
```

То же самое можно посмотреть через `objdump -s -j .data app`.

Массив реально лежит в файле как есть — покажем его сырым hex-дампом всего
файла (ищем первые байты `44 33 22 11`):

```bash
xxd app | grep -i "4433 2211"
```
```
00003010: 4433 2211 8877 6655 4455 6677 0011 2233  D3"..wfUDUfw.."3
```

`0x00003010` — это уже смещение в самом файле на диске.

## 3. `.bss` в файле НЕ хранится: `readelf -S`

Тип секции показывает, есть ли байты в файле:

```bash
readelf -S app | grep -E "Name|\.data|\.rodata|\.bss"
```
```
  [16] .rodata   PROGBITS  ...   <- байты в файле
  [25] .data     PROGBITS  ...   <- байты в файле
  [26] .bss      NOBITS    ...   <- байтов нет, только размер
```

## 4. Наглядный эксперимент: `.data` толстит файл, `.bss` — нет

Два одинаковых по размеру массива (1 МБ), отличаются лишь наличием
инициализатора — [`big_data.c`](big_data.c) (.data) и [`big_bss.c`](big_bss.c) (.bss):

```bash
gcc -O0 big_data.c -o big_data
gcc -O0 big_bss.c  -o big_bss
ls -l big_data big_bss
```
```
1064392  big_data     <- ~1 МБ: массив хранится в файле
  15800  big_bss       <- крошечный: в файле только "нужен 1 МБ нулей"
```

`size` показывает, куда ушёл этот мегабайт:

```bash
size big_data big_bss
```
```
   text     data      bss   filename
   1229  1049136        8   big_data     <- мегабайт в data (в файле)
   1229      544  1048608   big_bss      <- мегабайт в bss (НЕ в файле)
```

## Вывод

- Глобальный массив **с начальными значениями** едет в бинарник целиком
  (`.data`/`.rodata`, PROGBITS) — поэтому большие такие массивы раздувают файл.
- Глобальный массив **без значений** попадает в `.bss` (NOBITS): в файле лежит
  только размер, а сама память из нулей появляется уже при запуске.
- Локальный массив в файле не хранится — он рождается на стеке во время работы.

## Бонус: глобальный массив как кэш — [`fib.c`](fib.c)

Практический пример, где глобальный массив в `.bss` работает как таблица
мемоизации. `memo` объявлен без инициализатора, поэтому лежит в `.bss` и на
старте уже полон нулей — их и используем как «ещё не посчитано» (безопасно,
ведь `fib(n) > 0` при `n >= 2`):

```c
unsigned long long memo[MAXN];   // глобальный -> .bss -> нули на старте
...
if (memo[n]) return memo[n];         // 0 == ещё не считали
return memo[n] = fib(n-1) + fib(n-2); // посчитали и запомнили
```

```bash
gcc -O0 -std=c11 fib.c -o fib && ./fib
```
```
fib(93) = 12200160415121876738
всего вызовов fib(): 201        <- линейно, а не экспоненциально
```

`nm fib | grep -E "memo|calls"` подтверждает: и кэш, и счётчик — в .bss (буква `B`).

## Инструменты (шпаргалка)

| хочу | команда |
|------|---------|
| в какой секции символ | `nm app \| grep <имя>` |
| размеры text/data/bss | `size app` |
| hex-дамп секции | `readelf -x .data app` |
| дамп секции (иначе) | `objdump -s -j .data app` |
| список секций и их тип | `readelf -S app` |
| найти байты в файле | `xxd app \| grep <hex>` |
